# 云边混合 WebRTC 家庭监控系统技术架构方案

## 1. 方案结论

本项目采用 **云边混合 WebRTC Mesh 架构**：

- 家庭云作为主服务节点，承载信令服务和前端页面。
- 旧安卓手机作为采集端，连接家庭 Wi-Fi，并已加入 Tailscale。
- Tailscale 提供私有网络访问通道，适合自用设备在外网低成本访问。
- 阿里云作为公网网关，提供 HTTPS 入口、WebSocket 反向代理和 coturn STUN/TURN 兜底。
- WebRTC 媒体流优先 P2P 直连；当公网 NAT 穿透失败时，才通过阿里云 TURN 中继。

这个方案是合理的，而且比单一路线更稳妥：

- 比“纯家庭云公网暴露”安全，家庭网络不需要直接开端口。
- 比“全部服务部署阿里云”更省流量，常用链路不消耗云服务器带宽。
- 比“只依赖 Tailscale”更通用，家人或临时设备不用安装 VPN 也能访问。
- 比“只依赖 STUN”更可靠，因为 TURN 提供了最终兜底路径。

需要注意：Nginx 只能够代理 HTTP/HTTPS/WebSocket，不能代理 WebRTC 的 UDP 媒体流。公网观看是否稳定，关键不在 Nginx，而在 coturn 是否正确部署、端口是否放行、WebRTC ICE 配置是否正确。

## 2. 总体架构

```text
                             Public Internet
                                   |
                                   | HTTPS / WSS
                                   v
                         +--------------------+
                         |  aliserver 阿里云网关 |
                         |  100.115.222.54     |
                         |                    |
                         |  Nginx             |
                         |  - HTTPS 入口       |
                         |  - WebSocket 反代   |
                         |                    |
                         |  coturn            |
                         |  - STUN            |
                         |  - TURN relay      |
                         +----------+---------+
                                    |
                                    | Tailscale 私有网络
                                    v
+--------------------+  Wi-Fi / LAN / TS   +--------------------+
| mi10ultra Camera   | <-----------------> | homeserver         |
| 100.126.250.4      |                     | 100.65.192.69      |
| Browser            |                     | Node.js signaling  |
| getUserMedia       |                     | Static web hosting |
| SimplePeer         |                     | Tailscale / IPv6   |
+--------------------+                     +--------------------+
```

核心原则：

- **控制面**：HTTP 页面、WebSocket 信令走家庭云；公网入口由阿里云 Nginx 反代。
- **媒体面**：视频流走 WebRTC，优先 P2P，必要时走阿里云 coturn 中继。
- **私有面**：家庭云、阿里云和旧手机都已接入 Tailscale，不需要暴露家庭云公网端口。

### 2.1 当前 Tailscale 节点


| 节点           | 角色                     | Tailscale IP     |
| ------------ | ---------------------- | ---------------- |
| `homeserver` | 家庭云，信令服务和前端托管        | `100.65.192.69`  |
| `aliserver`  | 阿里云公网网关，Nginx + coturn | `100.115.222.54` |
| `mi10ultra`  | 旧安卓手机采集端               | `100.126.250.4`  |


该表记录规划中的节点身份和固定 Tailnet 地址，不表示实时在线状态；部署排障时以 `tailscale status` 和 `tailscale ping <节点>` 为准。

## 3. 物理节点与职责

### 3.1 家庭云：边缘计算中心

网络条件：

- 家庭 Wi-Fi 内网已连接。
- 含有 IPv6 地址。
- 已加入 Tailscale，虚拟 IP 为 `100.65.192.69`。
- 启用 Tailscale MagicDNS 和 HTTPS Certificates。

承载服务：

- Node.js 信令服务器。
- socket.io WebSocket 服务。
- 前端静态资源托管。
- 房间、角色、连接状态管理。

职责边界：

- 负责 camera 和 viewer 的信令撮合。
- 负责托管采集端和观看端网页。
- 不负责视频转发、录制、转码。
- 不直接暴露到公网，公网访问由阿里云反代进入。

### 3.2 旧安卓手机：采集终端

网络条件：

- 家庭 Wi-Fi 内网已连接。
- 含有 IPv6 地址。
- 已加入 Tailscale，虚拟 IP 为 `100.126.250.4`。
- 可通过家庭 Wi-Fi 内网或 Tailscale 地址访问采集端页面。

承载能力：

- 浏览器打开采集端 H5。
- 调用 `navigator.mediaDevices.getUserMedia()` 获取摄像头和麦克风。
- 使用 simple-peer 为每个观看端建立独立 WebRTC 连接。
- 房间开启陌生人告警时，在采集端浏览器执行 MediaPipe 检测、face-api 比对、截图合成和告警触发；服务端目前不解码视频。

关键职责：

- 本地预览摄像头画面。
- 加入指定房间，声明角色为 `camera`。
- 维护 `Map<viewerSocketId, SimplePeer>`。
- 每来一个 viewer，就创建一个独立 peer。
- viewer 离线时销毁对应 peer。

### 3.3 阿里云服务器：公网网关

服务器配置：

- 2 核 CPU。
- 2GB 内存。
- 40GB 系统盘。
- 200M 带宽。
- 独立公网 IPv4。
- 已加入 Tailscale，虚拟 IP 为 `100.115.222.54`。

承载服务：

- Nginx：公网 HTTPS 入口和 WebSocket 反向代理。
- coturn：STUN/TURN 服务。

职责边界：

- Nginx 只处理 HTTP、HTTPS、WebSocket。
- coturn 单独处理 WebRTC NAT 穿透和 TURN 中继。
- 阿里云不承载主业务状态，尽量保持为网关和兜底节点。

## 4. 双链路访问设计

### 4.1 链路 A：内网 / Tailscale 通道

适用场景：

- 你在家连接同一个 Wi-Fi。
- 你在外面，但主力手机或电脑已经开启 Tailscale。
- 你希望最低延迟、最低成本、最少公网暴露。

访问方式：

```text
Viewer -> homeserver 内网 Wi-Fi IP / IPv6 / 100.65.192.69 -> Web App + Signaling
```

（IPv6 必须在路由器开放防火墙，内网 IP 和 Tailscale IP 不需要开放外网端口）

媒体连接：

```text
Viewer <==== WebRTC P2P ====> Camera
```

链路特点：

- 不经过阿里云 Nginx。
- 不消耗阿里云流量。
- 在局域网内通常连接最快。
- 通过 Tailscale 访问时，WebRTC 可以在 `homeserver`、`mi10ultra` 和 viewer 的 Tailnet 地址之间生成候选路径；实际是否选择 Tailscale 路径，以 ICE 选路结果为准。

现在 `mi10ultra` 也已接入 Tailscale，因此私有通道更完整。仍需注意：WebRTC 媒体是否经过 Tailscale 由 ICE 自动选择，不应在业务逻辑里假设固定路径。要强制媒体经服务器中继，需要 TURN 或 SFU，而不是 Nginx。

### 4.2 链路 B：阿里云公网便捷通道

适用场景：

- 外部设备没有安装 Tailscale。
- 希望通过公开域名访问。
- 给家人临时使用。
- 需要公网可达的统一入口。

访问方式：

```text
Viewer
  -> https://www.kaitool.top/surveillance
  -> aliserver Nginx (100.115.222.54)
  -> Tailscale
  -> homeserver Node.js / Web App (100.65.192.69)
```

信令连接：

```text
Viewer
  -> WSS /surveillance/socket.io/
  -> aliserver Nginx
  -> homeserver socket.io
```

媒体连接：

```text
优先：Viewer <==== WebRTC P2P ====> Camera
兜底：Viewer <==== TURN relay on Aliyun ====> Camera
```

链路特点：

- 页面和信令通过阿里云公网域名进入。
- 视频流不经过 Nginx。
- P2P 成功时，阿里云只承担信令和少量 STUN。
- P2P 失败时，TURN 会消耗阿里云带宽和流量。

## 5. WebRTC Mesh 连接模型

第一阶段仍采用 Mesh：

```text
Camera -> Viewer A
Camera -> Viewer B
Camera -> Viewer C
```

每个观看端都有一个独立 peer：

```ts
const peers = new Map<string, SimplePeer.Instance>()
```

优点：

- 实现简单。
- 不需要媒体服务器。
- 局域网和少量观看端延迟低。

限制：

- 旧手机上行带宽随观看端数量线性增长。
- 多人观看会增加旧手机 CPU、编码、发热和电量压力。
- 第一阶段建议限制 1 到 2 个观看端。

容量估算应使用诊断面板中的实际发送码率：

```text
总上行带宽 = 各 viewer 实际发送码率之和

示例：若实测每路稳定在 4 Mbps
1 个 viewer 约 4 Mbps
2 个 viewer 约 8 Mbps
4 个 viewer 约 16 Mbps
```

当前分辨率优先档的编码上限约为 0.9～30 Mbps，帧率优先档允许最高 30 Mbps；浏览器会根据采集能力和网络动态选择实际值，不能仅凭“720p/1080p”推断固定码率。

如果后续希望多人稳定观看，应评估 SFU 架构，而不是继续扩大 Mesh。

## 6. 信令服务设计

### 6.1 房间模型

```ts
type Role = 'camera' | 'viewer'

interface RoomState {
  cameraSocketId?: string
  viewers: Set<string>
}

interface ClientState {
  roomId: string
  role: Role
}
```

约束：

- 第一阶段一个房间只允许一个 camera。
- 一个房间允许多个 viewer。
- viewer 可以在 camera 离线时进入等待状态。
- camera 离线后，所有 viewer 应收到状态通知。

### 6.2 加入房间

加入前，`roomId` 必须已由后台创建且策略为 `enabled: true`。当前实现还要求共享的 `ROOM_TOKEN`；它会进入前端构建产物，只适合受控的私有 MVP。

```ts
socket.emit('join-room', {
  roomId: 'home',
  role: 'camera',
  token: roomToken
})
```

或者：

```ts
socket.emit('join-room', {
  roomId: 'home',
  role: 'viewer',
  token: roomToken,
  deviceName: '客厅平板' // 可选，最长 80 个字符
})
```

服务端逻辑：

- camera 加入时记录 `cameraSocketId`。
- viewer 加入时加入 `viewers` 集合。
- 如果 viewer 加入且 camera 在线，通知 camera 创建 peer。

```ts
io.to(cameraSocketId).emit('viewer-joined', {
  viewerSocketId
})
```

### 6.3 信令透传

客户端发送：

```ts
socket.emit('signal', {
  roomId: 'home',
  to: targetSocketId,
  signal: data
})
```

服务端只转发：

```ts
io.to(to).emit('signal', {
  from: socket.id,
  signal
})
```

服务端不要解析、存储或打印完整 SDP，避免泄漏网络信息。

### 6.4 断开清理

推荐事件：

```ts
'viewer-left'
'camera-left'
'room-error'
```

断开处理：

- viewer 断开：从房间移除，并通知 camera 销毁对应 peer。
- camera 断开：清空房间 camera，并通知所有 viewer 当前监控源离线。

## 7. HTTPS 策略

这是本方案最容易踩坑的部分。

浏览器要求：调用 `navigator.mediaDevices.getUserMedia()` 必须在安全上下文中执行。通常只有以下场景可用：

- `https://...`
- `http://localhost`
- 部分浏览器认可的本地安全上下文

不能依赖：

```text
http://192.168.1.100:3333
```

旧安卓手机访问家庭云时，如果页面不是 HTTPS，摄像头授权大概率失败。

推荐方案：

1. 公网域名通过阿里云 Nginx 配置 Let's Encrypt 证书。
2. 家庭云启用 Tailscale MagicDNS 和 HTTPS Certificates。
3. 旧手机 `mi10ultra` 已接入 Tailscale，优先访问家庭云的 Tailscale HTTPS 域名，而不是裸 IP HTTP。

示例：

```text
https://home-server.your-tailnet.ts.net/surveillance/camera/home
```

需要提前验证：旧安卓手机浏览器是否能正常访问 Tailscale HTTPS 域名。由于 `mi10ultra` 已接入 Tailscale，理论上可以直接访问 Tailnet 私有域名或 `100.65.192.69`，但摄像头权限仍建议使用 HTTPS 域名而不是裸 IP。可选方案包括：

- 开启 Tailscale 的 MagicDNS 和 HTTPS 功能，解决证书问题。
- 让旧手机通过公网域名访问阿里云，再由阿里云反代回家庭云。
- 在家庭局域网 DNS 中给家庭云配置内网域名，并使用受信任证书。
- 在家庭云上使用本地域名和局域网可信证书，但这对手机证书信任配置要求更高。

## 8. Nginx 反向代理设计

阿里云 Nginx 负责公网入口：

```text
https://www.kaitool.top/surveillance
```

它应该反向代理到家庭云的 Tailscale IP `100.65.192.69` 或 MagicDNS 域名。

### 8.1 页面、API 与 Socket.IO 统一代理

当前生产配置使用 `PUBLIC_BASE_PATH=/surveillance`，因此页面、API 和 Socket.IO 都保留此前缀。不要把 `proxy_pass` 写成以单独的 `/` 结尾的上游地址，否则 Nginx 会剥掉 `/surveillance` 前缀。

```nginx
location /surveillance/ {
    client_max_body_size 15m;
    proxy_pass http://100.65.192.69:3333/surveillance/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

这一条 location 同时覆盖静态页面、`/surveillance/api/*` 和 `/surveillance/socket.io/`。若改用根路径部署，则前后端 base、Socket.IO path 和 Nginx location 必须一起改为根路径。

## 9. coturn 与阿里云安全组

coturn 是公网访问稳定性的关键，不是可有可无的附属组件。

### 9.1 为什么 Nginx 不够

Nginx 代理的是 HTTP、HTTPS、WebSocket，属于控制面。

WebRTC 视频流主要使用 UDP，属于媒体面。媒体面不走 Nginx，也不能靠 Nginx 转发。公网 P2P 失败时，必须由 TURN 服务器中继。

### 9.2 端口要求

阿里云安全组至少放行：

```text
TCP 80      # Let's Encrypt HTTP-01 或重定向
TCP 443     # HTTPS / WSS
UDP 3478    # STUN/TURN
TCP 3478    # TURN over TCP fallback，可选但建议
UDP 49152-65535 # TURN relay 端口范围，可按配置收窄
```

建议将 TURN 中继端口范围收窄，便于安全组管理，例如：

```text
UDP 49160-49200
```

对应 coturn 配置中设置：

```text
min-port=49160
max-port=49200
```

### 9.3 ICE 配置

前端统一使用可配置的 ICE servers：

```ts
const iceServers = [
  { urls: 'stun:stun.l.google.com:19302' },
  { urls: 'stun:global.stun.twilio.com:3478' },
  {
    urls: [
      'turn:www.kaitool.top:3478?transport=udp',
      'turn:www.kaitool.top:3478?transport=tcp'
    ],
    username: 'turn-user',
    credential: 'turn-password'
  }
]
```

生产环境不建议把长期固定 TURN 密码写死在前端。更好的做法是由后端签发短期 TURN 凭证。

## 10. 采集端流程

```text
打开 camera 页面
  -> 检查 HTTPS 安全上下文
  -> 请求摄像头/麦克风权限
  -> 本地 video 静音预览
  -> 连接 socket.io
  -> join-room(camera)
  -> 等待 viewer-joined
  -> 为每个 viewer 创建 SimplePeer initiator
  -> signal 通过 socket.io 透传
  -> WebRTC 建连
```

采集端 peer 配置：

```ts
const peer = new SimplePeer({
  initiator: true,
  stream: localStream,
  config: { iceServers }
})
```

建议采集端 UI 展示：

- 摄像头权限状态。
- socket 连接状态。
- 当前房间号。
- 当前观看人数。
- 每个 viewer 的 WebRTC 连接状态。
- 是否正在走 TURN relay。

## 11. 观看端流程

```text
打开 viewer 页面
  -> 连接 socket.io
  -> join-room(viewer)
  -> 等待 camera 发来的 offer
  -> 创建 SimplePeer non-initiator
  -> signal 通过 socket.io 透传
  -> 收到 stream
  -> 绑定 video 播放
```

观看端 peer 配置：

```ts
const peer = new SimplePeer({
  initiator: false,
  config: { iceServers }
})
```

观看端 UI 应展示：

- camera 是否在线。
- 信令连接状态。
- WebRTC 连接状态。
- 当前候选路径类型：`host`、`srflx`、`relay`。
- 失败时的重连按钮和错误说明。

## 12. 安全设计

公网入口必须加访问控制。监控系统不应只靠“链接很隐蔽”保护。

当前已经实现：

- 公网部署可使用 HTTPS/WSS。
- `join-room` 校验共享 `ROOM_TOKEN`，房间必须存在且启用。
- 服务端限制单房间最大 viewer 数，并校验信令双方属于同一房间且角色不同。
- 后台 API 使用独立 `ADMIN_TOKEN`。
- coturn 示例启用鉴权，不开放匿名 relay。

当前仍未实现或不足：

- `VITE_ROOM_TOKEN` 会进入前端构建产物，不能视为真正的公网秘密。
- 没有按用户、设备、角色和房间签发的短期 token。
- `GET …/api/ice-servers` 当前不鉴权；若返回长期 TURN 密码会造成滥用风险。
- 服务端尚未实现登录、join-room、Socket 消息和大请求的频率限制。
- 家庭成员接口会向持有共享 room token 的客户端返回完整识别数据。
- 房间 ID 应使用随机值；日志不得打印完整 SDP、ICE candidate、token 或 TURN credential。

后续应优先实现短期分角色 token、TURN 临时凭据、接口最小化和限流，详见 [TODO](6.TODO.md)。
