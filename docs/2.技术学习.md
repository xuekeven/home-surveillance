# 技术学习

## 云边混合架构

“云边混合”（Cloud-Edge Hybrid / Edge-Cloud Synergy）是现代物联网（IoT）和复杂大型软件系统中非常核心且高级的一种架构思想。

简单来说，它就是把“云端（中心化的公有云）”和“边缘端（靠近数据源的本地计算节点）”的优势完美结合起来，让它们各司其职、协同工作。

### ☁️ 1. 什么是“云” (Cloud)？

“云”指的是集中式的数据中心，比如你的**阿里云服务器**。

- **它的特长**：通常具备稳定的公网入口、可购买的带宽和较完善的运维能力，适合承担统一入口与中继。实际可用性和吞吐取决于实例、线路、带宽计费与部署方式。
- **它的短板**：**贵，且距离物理现场远。** 如果你把视频画面全都传到阿里云去处理，不仅会产生高昂的流量费，而且就算你在家里看监控，视频数据也得先跑到几百公里外的机房再绕回来，白白增加了延迟。

### 🏠 2. 什么是“边” (Edge)？

“边”指的是**边缘计算（Edge Computing）**，就是在靠近数据产生的“物理现场”部署算力。在你的方案里，你的**家庭云（NAS/软路由）和那台旧手机**，就是“边缘节点”。

- **它的特长**：靠近数据源，局域网通常延迟较低且不消耗公网流量；视频在 P2P 成功时可以不经过公有云。实际带宽、延迟、安全性和算力仍取决于家庭网络、设备配置与访问控制。
- **它的短板**：是个“孤岛”。因为通常没有公网 IP，出了家门就很难访问到它。

### 🤝 3. 什么是“云边混合” (协同)？

如果纯用“云”，太贵太慢；如果纯用“边”，出去了连不上。

**“云边混合”的精髓就是：把脏活、累活、私密活交给“边”；把抛头露面、统筹调度的活交给“云”。**

在你的终极架构里，这种协同体现得淋漓尽致：

1. **边缘做核心计算（Edge Computing）**：
  - 你的家庭云（边缘）负责跑 Node.js，处理复杂的 WebRTC 信令逻辑。
  - 旧手机（更极端的边缘）负责就地调用硬件编码视频流。
  - **好处**：省下了云服务器极其昂贵的 CPU 和流量成本。
2. **云端做网关与调度（Cloud Gateway）**：
  - 你的阿里云（云端）只负责挂一个 Nginx 和 Coturn。它就像一个“公网门面”和“指路牌”。
  - 当你在外面的蜂窝网络下想看监控时，阿里云这个“总机”接听了你的请求，然后通过 Tailscale 隧道把你的请求“转接”给家里的边缘服务器。

### 💡 一个直观的比喻

你可以把“云边混合”想象成一家**跨国餐饮连锁店**：

- **边缘端（边）**：就是各地街道的**实体门店（后厨）**。蔬菜在这里切，肉在这里炒，顾客在这里直接吃（处理本地数据）。反应最快，效率最高。
- **云端（云）**：就是**全球总部（客服中心/广告牌）**。总部不负责炒菜（不处理沉重的视频流），它只负责挂出全球统一的 400 电话（公网域名）。当有顾客打电话订餐时，总部把订单路由（转发）给离顾客最近的那个实体门店。

把信令和静态页面部署在家庭云、用阿里云提供公网入口和必要的 TURN 中继，可以在延迟、成本与可访问性之间取得适合家庭监控的平衡。

## WebRTC

WebRTC（Web Real-Time Communication）是目前浏览器端实现超低延迟实时音视频通讯的行业标准。要构建一个从“单兵作战”到“万人直播”的系统，核心在于理解并选择合适的底层拓扑架构。目前业界主要有三大架构：Mesh、SFU 和 MCU。

### 一、 Mesh 架构 (全分布式点对点)

Mesh 不引入 SFU/MCU，每对需要通信的参与者建立独立的 PeerConnection。本项目是“一台 camera 向多个 viewer 发送”，不是所有参与者彼此互发。

- **工作机制**：camera 为每个 viewer 建立一条独立连接。浏览器可能复用部分采集与编码能力，但上行流量和 PeerConnection 数量仍随 viewer 数量增长。
- **服务器角色**：信令服务器交换 SDP/ICE；STUN 辅助发现公网映射；直连失败时 TURN 会转发加密媒体包。因此只有 P2P 成功时，媒体才不经过中继服务器。
- **优势**：
  - 实现和部署相对简单，不需要维护 SFU/MCU。
  - 少量观看端且 P2P 成功时，服务端带宽成本较低。
  - WebRTC 媒体在传输中加密；但端点安全、凭据和浏览器权限仍决定整体隐私。
- **瓶颈**：
  - viewer 增加会提高旧手机的编码、连接管理、发热和功耗压力。
  - camera 上行带宽按连接数增长；走 TURN 时还会消耗中继带宽。
- **适用**：1 对 1 或 1 对少量观看端的家庭监控。

### 二、 SFU 架构 (Selective Forwarding Unit - 选择性转发单元)

SFU 是多人实时音视频常见的拓扑之一。它引入中心媒体服务器，通常以转发 RTP/媒体包为主，并可根据订阅、带宽和 simulcast/SVC 层选择不同质量。

- **工作机制**：每个客户端只需要将自己的音视频流**上传 1 次**给 SFU 服务器。SFU 服务器就像一个聪明的路由器，它根据各个客户端的订阅需求，把这路流**原封不动地复制并分发**给其他人。
- **服务器角色**：充当星型拓扑的中心节点，只负责数据包的路由转发，**不进行任何视频解码或重新编码**。
- **优势**：
  - **解放客户端上行**：无论房间里有多少人，你的设备永远只需要编码并上传 1 路流，CPU 和上行带宽压力骤降。
  - **超低延迟**：服务器只转发不处理，几乎不增加额外的端到端延迟。
  - **可扩展性较好**：相较 MCU 不必对每路视频持续解码和重编码，但容量仍受网卡、带宽、包处理、加密、质量层和实现方式影响，必须压测。
- **劣势**：
  - **下行带宽依然很高**：虽然上行只有 1 路，但如果房间里有 50 个人开启摄像头，客户端需要同时下载并渲染 49 路流，对手机的下行网络和渲染性能依然有挑战（通常通过动态降低非核心人员的分辨率来缓解）。
- **主流开源组件**：`mediasoup`, `LiveKit`, `Janus`。

### 三、 MCU 架构 (Multipoint Control Unit - 多点控制单元)

这是最重型、最传统、也是“最昂贵”的架构方案。它不仅是“搬运工”，更是“超级加工厂”。

- **工作机制**：每个客户端将自己的音视频流上传给 MCU 服务器。MCU 服务器将收到的所有视频流**全部解码**，然后在服务器内存中**重新拼图、混合**（比如拼成一个九宫格大画面），接着再**重新编码**成单一视频流，最后下发给各个客户端。
- **服务器角色**：全权接管音视频的解码、混流和编码。
- **优势**：
  - **客户端负担极小**：无论开会的人多少，客户端永远只上传 1 路流并且**只下载 1 路流**（那个已经拼好的大画面）。
  - **极致兼容性**：连性能极差的老古董手机或传统的硬件视频会议终端都能毫无压力地接入，因为它们只需要播放一路普通的视频流。
- **劣势**：
  - **服务器成本**：实时视频解码和重编码是极其昂贵的操作，对云服务器的 CPU 和 GPU 算力消耗极大，成本极高。
  - **延迟增加**：中间增加了解码、合成和重新编码，延迟通常高于纯转发；具体数值取决于编码参数、硬件和实现，不能固定为 200ms。
  - **布局死板**：客户端只能看服务器拼好的固定画面，无法像 SFU 那样在本地自由放大某个人的窗口。
- **适用**：传统安防硬件上云、老旧硬件视频会议系统整合、极高并发但只纯看（如 WebRTC 转 RTMP 千万人直播源）。

### 四、 极客总结与选型指南

- **观看端很少、希望部署简单**：优先评估 **Mesh**，但仍需要信令服务并准备 TURN 兜底。
- **多人互动、希望降低采集端上行压力**：评估 **SFU**，容量与成本必须结合实际码率压测。
- **需要服务端混画或兼容只接收单路媒体的终端**：评估 **MCU**；大规模单向直播通常还会结合 CDN，而不是只靠 MCU。

## Coturn 服务

在 WebRTC 架构中，coturn 是常用的开源 **STUN/TURN** 服务器实现。STUN、ICE 与 TURN 共同处理候选发现、连通性检查和中继兜底；TURN 是直连失败时常见且可靠的媒体中继方案。

### 一、 为什么需要 Coturn？

在理想的互联网，设备间可直接通过 IP 通信。但在现实中，绝大多数设备都躲在 **NAT（网络地址转换）** 路由器后面。

1. **STUN (发现)**：告诉躲在路由器后面的设备：“你的公网 IP 和端口是多少”。如果网络环境简单，双方知道了彼此的公网 IP，就能建立 P2P 直连。
2. **TURN (中继)**：当双方都处于极其严格的网络（如对称型 NAT）下，打洞会彻底失败。此时，Coturn 充当“传声筒”，所有视频流量先发给 Coturn，再由它转发给对方。

### 二、 Coturn 在云边混合架构中的角色

在你的监控系统方案中，Coturn 建议部署在 **阿里云公网服务器** 上。

- **可达性要求**：生产 TURN 需要稳定、可从公网访问的地址和端口；常用固定公网 IP 配合域名。若服务器位于云厂商 VPC/NAT 后，还要正确配置公网与私网地址映射。
- **作为保底方案**：当你在外网（如 5G 网络）无法与家里的旧手机建立 P2P 直连时，阿里云上的 Coturn 会自动接管流量，确保你依然能看到监控画面。

### 三、 核心配置参数 (turnserver.conf)

安装 Coturn 后，最核心的工作是配置 `turnserver.conf`。以下是极客常用的关键配置项：

```conf
# 监听端口（默认 3478）
listening-port=3478

# 外部公网 IP（非常重要，填阿里云的公网 IP）
external-ip=47.xxx.xxx.xxx

# 域名与认证（TURN 强制要求身份校验）
realm=your-domain.com
user=myuser:mypassword

# 流量中继的 UDP 端口范围（需在安全组放行）
min-port=49152
max-port=65535

# 运行模式
fingerprint
```

### 四、 部署时的“三大深水坑”

1. 安全组权限（最常见错误）：
  - 不仅要开启 3478 的 UDP 和 TCP 端口。
  - 必须开启你在配置文件中设置的 min-port 到 max-port 之间的所有 UDP 端口。如果这部分没开，打洞能成功，但视频流会卡死。
2. 双重 NAT 环境：
  - 如果服务器本身也在内网（如阿里云的 VPC），必须配置 external-ip 映射，否则 Coturn 返回给客户端的将是服务器的私有内网 IP，导致连线失败。
3. 流量超支风险：
  - TURN 转发是实打实消耗服务器带宽的。如果你的监控画面是 4K/60 帧且打洞失败走中继，你的阿里云带宽峰值和流量包会消耗得极快。

### 五、 如何检测 Coturn 是否正常工作？

不要急着写代码，先用调试工具验证服务器：

- 访问 [Trickle ICE 调试工具](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/)。
- 输入你的服务器地址 `turn:你的公网IP:3478` 以及账号密码。
- 点击 Gather candidates。
  - 如果能看到类型为 `srflx` 的条目，说明 STUN 正常。
  - 如果能看到类型为 `relay` 的条目，说明 TURN 中继 彻底跑通。

## coturn 和 Tailscale

两者都能帮助 NAT 后的设备通信，但服务对象不同，不能互相替代：

- **Tailscale** 在操作系统网络层提供 Tailnet。它使用协调服务分发节点与密钥信息，使用 STUN 等技术尝试建立直接 UDP 路径；直接路径不可用时，DERP 转发加密的 Tailscale/WireGuard 流量。
- **coturn** 为 WebRTC 提供 STUN/TURN。浏览器通过 ICE 收集和测试候选；无法直连时，TURN 为当前 WebRTC 会话分配 relay candidate 并中继加密媒体包。
- Tailscale 没有使用 coturn 作为其数据中继。DERP 与 TURN 都承担“直连失败后的中继”角色，但协议、客户端、转发的数据和适用范围不同。

在本项目中存在两套相互独立的选择：

1. 页面、API 和 Socket.IO 可以通过 Tailscale 直接访问家庭云，也可以通过阿里云 Nginx 公网入口访问。
2. 浏览器之间的 WebRTC 媒体仍由 ICE 独立选路：可能 P2P，也可能回退到阿里云 coturn。通过 Tailscale 打开页面并不保证媒体一定经过 Tailscale；通过公网域名打开页面也不代表媒体一定经过阿里云。

排查 Tailscale 路径可使用 `tailscale status`、`tailscale ping` 和 `tailscale netcheck`；排查 WebRTC 路径应查看本项目诊断面板中的 ICE candidate 类型。参考：[Tailscale STUN](https://tailscale.com/docs/reference/stun-protocol)、[DERP servers](https://tailscale.com/docs/reference/derp-servers)、[NAT traversal](https://tailscale.com/blog/how-nat-traversal-works)。
